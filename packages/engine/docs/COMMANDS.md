# Commands and debugging details

The scripts in `package.json` forward to the CLI `threedog` (from `@threedog/tools`; the root `build` runs each workspace's own `build`);
**`threedog xxx` on this page means `node node_modules/@threedog/tools/bin/threedog.mjs xxx`** (in this repo: `node packages/tools/bin/threedog.mjs xxx`): plain node starts fastest; `npm run xxx` is the same (npx adds about 2.5 s per call).
Every command checks its options: an unknown one fails and lists the valid ones (`dev` / `build` / `preview` pass theirs to vite).

## Running one game only
After `-w` write the directory or the package name (inside a game directory a plain `npm run ...` does the same):
- Dev: `npm run dev -w games/my-game`, or from the root `npm run dev -- my-game` (part of the name is enough); no name means the engine example. To
  change the port (default 5173; if taken it moves to the next one): `npm run dev -- my-game --port 5000` (the game name must come first, the
  remaining arguments go to vite untouched; don't add another `--`).
- Test: `npm test -w games/my-game`, or `threedog test -w my-game`; `npm test` at the root tests every workspace (engine + each game).
- Build: `npm run build -w games/my-game`; `npm run build` at the root builds all (every *.html in a workspace root is bundled, no change to
  vite.config.js needed); under a sub-path of a site: `threedog build my-game --base /my-game/` (recipes/61-deploy.md).
- Screenshot / bake / compress models: `npm run shot -- -w my-game / --describe-only` (`--out day.png` your own name, still in `.threedog/shots/` (a path with a directory is written as given), `--tier low|high` render at that device tier (default: the desktop tier, skipped effects are named), `--keep` timestamped file name; the rest in the table below), `npm run bake -- -w my-game`, `npm run assets -- optimize -w my-game`.
- A game's tests: every `games/<game>/tests/specs/*.mjs` runs (each exports a `specs` array; the runner finds the files, nothing to register); without
  `tests/specs/` a smoke test runs automatically (page opens, engine ready, no console errors). Minimal example:
```js
// games/my-farm/tests/specs/farm.mjs — export a specs array, one entry per page
export const specs = [{
  name: 'farm: pick up apple',  // threedog test apple matches by name substring, any case
  url: '/?cutscene=skip',  // page path + URL parameters
  async run({ page, check, ev, frames, wait }) {
    // ev(fn, arg): runs in the page (engine is available). The function is serialized, so it can't use outer variables; pass them as the argument:
    const n = await ev(id => engine.inventory.count(id), 'apple');
    check('no apple at start', n === 0, `actual ${n}`);  // check(label, passed, details on failure)
    await page.keyboard.press('KeyE');  // page is a Playwright page: keys, clicks
    await frames(3);  // wait 3 frames of the real-time loop (software rendering is slow; waiting by frames is more reliable than wait(ms))
    check('has apple after pickup', await ev(id => engine.inventory.count(id), 'apple') > 0);
  },
}];
```
  Tests run against the built bundle (not the dev server): main.js must set `window.engine = engine;` before `await engine.start()`, otherwise the
  test waits for the engine until timeout (the error explains why).
  A spec whose run() reads pixels (`page.screenshot`) moves to software rendering, which is much slower; `software: false` on the spec keeps it on the GPU for a real picture. Frame times measured beside other pages read several times too high: give such a spec `serial: true`, or run with `--jobs 1`. A spec file and what it imports run in Node. Importing `threedog` there works, but a file that touches `document` or `window` at its top level fails: move that code into a function, move plain data into a file of its own, or read the value in the page through `ev`.
  A test that steers: `frames(n)` and `wait(ms)` follow the machine; hold the loop with `engine.haltLoop('my-test')` and advance game time yourself, `await page.keyboard.down('KeyW'); await ev(() => engine.step(0.25));`: the same steps give the same path on any machine.
- New game: `npm run new-game -- name [--open-world | --pixel] [--webgl]` (the blank and `--open-world` starts: `recipes/01-new-game.md`; `--pixel` starts a sprite character in a pixel-snapped orthographic view with input, interaction, dialogue and saves wired, gray placeholders, not together with `--open-world`; the game runs on WebGPU and writes shaders in TSL, `--webgl` on WebGL with GLSL).
- Game in your own folder (outside this repo): after `npm install threedog@1 three@~0.187.0 @threedog/tools@1`, run `node node_modules/@threedog/tools/bin/threedog.mjs init [folder] [--open-world] [--webgl]` (folder: the one to create, default the current folder): it copies the new-game template without overwriting anything, merges package.json and writes `.mcp.json`, so Claude Code opened in that folder starts the threedog MCP server by itself.

> Git Bash (MSYS) rewrites arguments that start with `/` into a path under the Git install (`/` turns into `C:/Program Files/Git/`). Page arguments (`shot`, `capture`, `--page`) undo that by themselves, through `npm run` too (npm still echoes `> threedog shot C:/...`; shot then prints the page it really opens); if the Git folder cannot be found the error says so: then write `shot styletest`, set `MSYS_NO_PATHCONV=1`, or use PowerShell.

> Windows PowerShell 5.1: `Get-Content` / `Set-Content` without `-Encoding utf8` read and write UTF-8 files in the system code page (mojibake, lost newlines). Pass `-Encoding utf8`, or edit files with your editor tools.

**`--json` result** (`check`, `test`): one line on stdout, `{ ok, summary, items: [{ code, level, file, line, message, fix }] }`. `level` is `error` or `warn`; a field is present only when known. `code` is the rule id (`R4`), a TypeScript code (`TS2345`), `content` or `test`. A test item's message is `<item name>: <check> → <reason>`; the totals are in `summary`. `ok` and the exit code agree.

## Dev bridge commands
They drive the running game. Run them inside the game folder or with `-w game`; at the repo root the one running dev server is used (several: the error lists them for `-w`). `threedog <command> --help` prints the same line. `recipes/16-dev-bridge.md`

## Reproducing a scenario and debugging
- Add `?time=18:30&weather=rain&pos=40,-20&save=slot1&cutscene=skip&state=name` to the URL (effective in development).
- In the console / tests: `engine.describeText()` reads the state as English text; `engine.step(seconds)` fast-forwards synchronously (no rendering);
  `engine.haltLoop()` stops the real-time loop.
- To wait for the page: `page.waitForFunction(() => window.engine?.stateApplied)` (start has finished and all URL parameters are applied), then read `engine.stateRefused` for what the URL could not do (`shot` and `capture` fail on it); never read
  `_`-prefixed private fields. An engine that cannot be reached within 40 seconds fails with the page status, the latest page errors and the fix.
- Advancing dialogue headlessly: recipe 02.
- Debug objects on window: `window.engine` is declared; for a game's own, `/** @type {any} */ (window).game = {...}`.
- To operate a running game: the dev bridge, `recipes/16-dev-bridge.md`.
